# 물방울 연구실 제작기 · 방울이의 물길 탐험

초등 4학년 과학 「물의 상태 변화」 웹게임을 기획부터 2026-10-25 스테이지 수정까지 어떻게 만들었는지 정리한다. 기획·제작은 옐샘 & 아이스크림미디어다.

이 글은 저장소에 남은 기획 문서, 검증 보고서, 커밋 기록만 근거로 썼다. **실제 수업 적용, 학생 반응, 학습효과는 아직 측정하지 않았다.** 아래 숫자는 모두 해당 날짜 보고서에 적힌 값이다.

## 1. 아이디어 — 무엇을 왜 만들었나

출발점은 「물방울 연구실 심화 설계안 v2.0」, 기존 PRD·TRD, 샘플 이미지였다(`docs/water-drop-lab_PRD.md`, 2026-09-23). 학생은 물방울 연구실의 신입 연구원이다. 중앙 코어가 멈춰 다섯 구역의 물길이 끊겼고, 관찰·측정·비교·증거 분석·설계로 연구 기록을 되찾아 물길을 복구한다. 방울이는 정답을 말해 주는 캐릭터가 아니라 **어디를 관찰하면 좋을지 알려 주는** 역할로 정했다.

처음부터 정한 원칙은 지금까지 유지된다.

- 관찰 없이 다음 단계로 넘어가지 않는다. 예상이 틀렸다고 감점하지 않는다.
- 마지막 복구는 자동 완료 버튼이 아니라 학생이 만든 장치와 기록으로 한다.
- 수증기는 눈에 보이지 않는 기체다. 흰 김이나 구름 캐릭터를 수증기로 그리지 않는다. 입자 운동으로 설명하지 않는다.
- 얼기 전후에는 무게가 같고 차지하는 공간이 커지는 관찰에 집중한다.
- 물높이·시간·수집 지수는 비교용 가상 값이다. 실제 배관 안전 기준이나 실제 물 생산량으로 쓰지 않는다.

화면은 **메인 → 연구섬 지도 → 실험 10장 → 결과·인증서**로 잡았다. 지도만 비스듬히 내려다보는 2.5D 그림이고, 실험과 장치 공방은 정면 2D다. 3D 엔진과 카메라는 쓰지 않았다.

## 2. 설계 — 놀이와 배움을 어떻게 묶었나

설계 문서는 다섯 개다. MVP PRD는 저장소 루트에, 나머지는 `docs/`에 있다.

| 날짜 | 설계 | 핵심 |
|---|---|---|
| 09-23 | MVP PRD | 10장 시나리오와 완료 조건. 장마다 다음 장으로 가져갈 기록을 정함 |
| 10-15 | 활동·시각 고도화 계획 | 앞 장의 결과가 다음 장의 재료가 되게 연결(관찰 사진 → 분류, 측정 기록 → 공간 판단). 속도·반복 클릭에는 보상하지 않음 |
| 10-16 | 태블릿 탐구 경험 설계 | 대표 경험 세 가지: 닦은 자리에 다시 생기는 물방울, 내 그림의 변화를 되돌려 보는 기록, 새는 물길을 고쳐 더 모으는 장치 |
| 10-21 | 물길 탐험 3.0 | 장마다 **기본 실험 → 현장 의뢰** 두 활동. 도장 10개·도구 5개·복구 그림·능력 문장 인증서 |
| 10-22 | 개념 영상 명세 | 현장 의뢰를 해결한 **뒤에** 보는 9초 영상. 정답을 먼저 보여 주지 않음 |

10장의 흐름은 다음과 같다.

| 장 | 학생이 하는 일 | 성취기준 |
|---|---|---|
| 1·2 | 두 그릇에 물 붓기·얼음 옮기기·젖은 천 관찰 → 실험·생활 장면을 세 상태로 분류 | [4과10-01] |
| 3·4 | 같은 물의 얼기 전후 높이·무게 측정 → 채움 정도를 바꿔 얼음이 커질 공간 비교 | [4과10-02] |
| 5·6 | 직접 그린 물그림의 시간 변화 → 가열하지 않은 물과 끓는 물 비교 | [4과10-02] |
| 7·8 | 밀봉한 차가운 컵 닦고 다시 생기는 물방울 관찰 → 내 증거로 설명하고 음료병에 적용 | [4과10-02] |
| 9·10 | 부품을 배치해 물 모으는 장치 시험·수정 → 내 장치로 코어의 고장 진단·수리 | [4과10-03] |

긴장은 제한 시간이 아니라 **예상과 결과의 차이, 조건이 맞지 않을 때의 실패**로 만든다. 실패하면 이유를 알려 주고 같은 자리에서 고친다. 가상 설계만으로 [4과10-03]의 '만들기'를 다 했다고 보지 않고, 교사용 안내에서 실제 만들기 활동으로 연결한다.

## 3. 구현 — 무엇으로 만들었나

화면 요소마다 맡는 일을 나눴다.

- **이미지**: 지도·배경·방울이·실험 도구의 생김새. 생성 이미지의 WebP를 실행에 쓰고, 다시 작업할 PNG 원본은 따로 보존한다.
- **Canvas(Phaser·현장 의뢰)**: 붓기, 끌기, 문지르기, 그리기, 시간 조절처럼 손으로 하는 조작과 물높이·기포·물방울 같은 관찰 상태.
- **DOM·SVG**: 질문, 안내, 기록, 설정, 그리고 끌기가 어려운 학생을 위한 버튼·탭 대체 조작.

저울 숫자, 물높이, 눈금, 물방울은 그림에 넣지 않고 코드로 그린다. 상태를 정확히 보여 주려면 실험 결과에 따라 바뀌어야 하기 때문이다.

| 영역 | 주요 파일 |
|---|---|
| 화면 전환·보상·인증서 | `src/app.js`, `src/journey.js` |
| 실험 모형·완료 조건 | `src/activity-model.js`, `src/inquiry-model.js`, `src/collector-model.js`, `src/domain.js` |
| 실험·현장 의뢰 화면 | `src/activities.js`, `src/inquiry.js`, `src/fieldwork.js`, `src/phaser-scenes.js`, `src/workshop.js` |
| 저장·설정·소리 | `src/state.js`, `src/settings.js`, `src/settings-content.js`, `src/sound.js` |
| 검사 | `tests/*.test.mjs`, `scripts/*-qa.py` |

소리는 직접 합성한 Web Audio 배경 음악과 Kenney의 CC0 효과음 7종이다. 개념 영상은 직접 작성한 SVG 장면을 sharp와 FFmpeg로 렌더했다. 글꼴(Jua)과 엔진(Phaser)도 저장소에 넣어 실행 중 외부 서버에 요청하지 않는다. 출처와 라이선스는 `public/assets/CREDITS.md`에 모았다.

## 4. 검증 — 어떻게 확인했나

검사는 매번 새 Chrome 임시 프로필과 별도 포트에서 했고, 사용자 브라우저의 학습 기록은 건드리지 않았다. 처음 실패한 결과도 지우지 않고 남겼다. 미리 준비한 기록에서 시작한 흐름 검사는 학생이 처음부터 끝까지 한 완주와 구분해 적었다.

|---|---:|---|
| 09-24 | 13개 | 메인 → 10장 → 코어 복구 → 결과까지 실제 브라우저 완주, 결함 8개 수정 |
| 10-15 | 27개 | 1~10장 수행, 1280×800 등 5개 화면 크기 |

내부 최종점검 점수(구현·설계 검수 점수이며 학생 대상 효과 측정이 아니다)는 2026-10-21 196/242, 2026-10-24 206/253이었다. 두 번 모두 교실 네트워크 항목은 0점이었다. 오프라인에서 새로고침하면 열리지 않기 때문이다.

**아직 확인하지 못한 것**

- 실물 태블릿의 손가락 터치(검사는 마우스·키보드·버튼 대안과 화면 크기 모사)
- 전자칠판 뒷자리 가독성, 교실 스피커 음량
- 학교 와이파이·30명 동시 접속, 오프라인 실행
- 실제 학생의 이해도 변화, 재미, 소요 시간
- 실물 물 모으기 장치 만들기

## 5. 무엇이 바뀌었고 왜 바꿨나

**버튼을 누르는 실험에서 손으로 하는 실험으로 (10-15, 10-18).** 학생의 조작이 모양·조건·관찰 위치·결과 중 하나를 실제로 바꿔야 관찰에 의미가 생긴다는 설계 원칙을 따랐다. 주전자 붓기, 얼음 이동, 손그림, 부분 닦기, 공방 부품 이동을 Phaser Canvas로 옮겼다. 캔버스에 가려진 버튼 대체 조작은 도구 패널에 다시 연결했다. 터치하는 손 기술을 학습 점수로 평가하지 않는다는 설계 원칙 때문이다.

**실험 하나에서 실험 + 현장 의뢰로 (10-21).** 기본 실험에서 본 것을 새 상황에 써 보게 하려고 장마다 현장 의뢰를 붙였다. 실험 완료 조건 없이는 의뢰가 열리지 않고, 의뢰를 해결해야 보상과 다음 구역이 열린다.

**정답 화면 대신 해결 후 개념 영상 (10-22).** 학생이 직접 해결한 뒤 9초 영상으로 개념을 다시 연결한다. 한글 설명은 영상에 굽지 않고 화면 글자로 보여 준다. 영상을 닫아도 진행이나 기록은 지워지지 않는다.

**시간 슬라이더 (10-24).** 소스 감사에서 실제로 쓰이는 1·5·6·7·8장 화면에는 시간 드래그가 없고, 쓰지 않는 예전 화면에만 남아 있다는 것을 찾았다. 52px 터치 영역의 시간 슬라이더를 넣었다. 뒤로 밀면 지난 모습을 보지만 기록은 덮어쓰지 않는다.

**그림 교체 (10-15 → 10-25).** 단순 도형이던 저울·탱크·응결판을 생성 이미지로 바꾸고(10-24), 구역마다 실험 배경 6종을 넣었다(10-25). 생활 장면 그림은 처음 생성본의 소품이 문항과 맞지 않아 다시 고쳤다. 수치와 판정은 계속 코드가 표시한다.

**스테이지 수정 (10-25).** 실제 진행을 다시 따라가며 학습 내용과 조작이 어긋나는 곳을 고쳤다.

- 4장 기본 실험(95% 한계)과 현장 의뢰(100% 한계)의 판정이 서로 반대 답처럼 보였다. 같은 부피 계산을 쓰고, 기본 목표 '빈 공간 5% 이상'과 의뢰 목표 '넘치지 않기'를 나눠 보여 준다.
- 5장에서 관찰한 뒤에도 처음 예상을 바꿀 수 있었다. 첫 관찰 때 예상을 고정하고, 관찰 뒤 생각은 따로 남긴다.
- 현장 의뢰의 실패 이유가 접힌 힌트 안에 있었다. 지금 할 일과 최근 결과를 펼쳐 둔다.
- 공방에서 겹친 부품을 누르면 다른 부품이 움직였다. 그림의 보이는 부분으로 선택하고 전용 이동 손잡이를 둔다.
- 저장 실패를 읽기·쓰기·충돌·원본 보호로 구분해 알려 준다. 학생 저장 키와 구조는 바꾸지 않았다.

**바꾸지 않은 결정.** 3D 엔진, 로그인, 시간 제한, 점수 경쟁은 넣지 않았다. 5구역·10개 발견·10개 의뢰·방울이·2.5D 지도와 2D 실험·여권·자기 설계 재사용은 처음 구조를 유지했다.

## 6. 남은 일

1. 오프라인 캐시와 새 버전 교체를 넣고 학교망에서 다시 시험한다.
2. 사용자 제공 그림(방울이 포함)과 생성 이미지의 상업 배포 권리를 회사와 확인한다.
3. 실물 태블릿·전자칠판·교실 스피커로 현장 점검을 한다.
4. 2·3장의 반복 동기가 약하다는 점검 결과가 있다. 실제 학생 반응을 본 뒤 보강 여부를 정한다.
5. 무가사 배경 음악(메인·엔딩)은 프롬프트만 준비했다(`docs/audio/SUNO-PROMPTS.md`).

날짜별로 무엇이 약했고 어떻게 확인했는지는 [기능향상기](기능향상기-물방울연구실.md)에 있다.

## 2026-10-25 최종점검 고도화

최종점검 23항목을 4해상도 캡처와 실측으로 다시 매기니 196/253이었다. 가장 낮은 두 곳은 오프라인 불가(19번 0점)와 13~14px 글자(12번 FAIL)였다. 사용자 승인 뒤 고도화했다.

- 그림: 크림색 평판이던 현장 의뢰 캔버스에 구역별 작업대 배경 5장을 넣었다. 6장 회색 막대는 가열판, 5장 반투명 판은 그림판, 10장 작은 보석은 물방울 코어 그림으로 바꿨다. 9·10장에는 사용자 샘플 페이지의 연구실 배경을 적용했다. 이야기상 마지막 두 장은 연구실 안이다.
